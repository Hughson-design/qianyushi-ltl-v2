# Justnano LTL 打单平台 V2：精简产品需求基线

- 文档版本：v0.4（精简版 + 客户押金，仅 BOL）
- 基线日期：2026-09-11
- 产品目标：先把询价、选价、下单和打印做简单、稳定、好用
- 当前范围终点：订单创建成功并取得 BOL

## 1. 首版产品定位

V2 首版不是完整 TMS，而是一套轻量的 LTL 询价和打单平台。

核心流程只有：

**客户/地址 → 填写货物 → 多渠道询价 → 选择 Rate → 检查押金 → 创建订单 → 生成 BOL 并扣除押金 → 下载/打印 BOL → 查询历史订单**

首版首先解决三个问题：

1. 不用在多个渠道之间重复输入相同资料。
2. 可以快速比较成本和客户售价。
3. 选定价格后，可以使用客户押金直接下单并打印文件。

## 2. 当前明确不做

以下内容不进入首版设计、开发和验收：

- Pickup 预约、修改或取消。
- Tracking、轨迹同步和运输异常。
- POD 获取和管理。
- Invoice、在线付款、信用额度和完整会计流程。
- Rebill、Adjustment 和客户申诉。
- 信用卡/ACH 在线充值和自动退款。
- Dashboard、复杂报表和利润分析中心。
- AI 识别邮件、BOL 或自动推荐 Carrier。
- 企业微信、短信和复杂通知系统。

这些功能以后是否增加，再根据实际使用情况决定。当前不为它们预建复杂模块。

## 3. 首版保留的关键原则

### 3.1 Quote 与 Order 分开

Quote 用于保存一次询价及返回的多条 Rate；Order 是选择某条有效 Rate 后形成的实际订单。

### 3.2 只有价格字段变化才重新询价

会使 Rate 失效的字段：

- 起运地和目的地 ZIP。
- 商业/住宅地址类型。
- 件数、包装类型、尺寸、重量。
- Freight Class、NMFC、Hazmat、Stackable。
- Liftgate、Residential、Limited Access、Appointment 等计费服务。

不会使 Rate 失效的字段：

- 联系人、电话、邮箱。
- PO、Reference Number。
- Dock Hours 和普通备注。

### 3.3 客户只看售价

系统内部保存渠道成本、加价和客户售价；客户账号只显示售价，不显示成本、毛利和上游渠道账号。

### 3.4 历史订单可以复制，但必须重新询价

复制地址、货物和服务选项；不复制旧 Rate、旧订单号、旧 PRO 或旧文件。

### 3.5 渠道接入保持简单

每个渠道只需要首版的三个能力：

1. 获取 Rate。
2. 创建 Order/Shipment。
3. 获取 BOL。

单个渠道失败不能影响其他渠道返回报价。

### 3.6 BOL 扣押金，Void 退押金

- 客户提交下单前，系统检查可用押金是否足够覆盖该票客户售价。
- 为防止同一客户同时下多票造成超额使用，提交时先在系统内部原子预占相应金额。
- 外部订单成功且 BOL 成功生成时，预占金额转为正式扣款。
- 外部下单或 BOL 生成失败时，预占金额立即释放。
- Void 经上游渠道确认成功后，按该订单原扣款金额全额退回客户押金。
- Void 失败或仍在等待渠道确认时不得先行退款。
- 同一订单最多只能成功扣款一次、退款一次；重复请求不得重复改变余额。
- 首版不根据后续承运商账单调整押金，Rebill 仍不在当前范围。

## 4. 首版用户与权限

只保留三个角色：

| 角色 | 权限 |
|---|---|
| Admin/Operations | 管理客户、地址、报价、价格、订单、渠道配置、文件和押金充值/调整 |
| Sales | 为负责的客户询价、查看价格、协助下单和查看订单 |
| Customer | 管理本公司的地址、查看押金与流水、询价、下单和下载本公司的文件 |

基本安全规则：

- 客户只能看到自己公司的数据。
- 客户页面和接口不得返回成本、毛利、渠道凭证和内部备注。
- 人工修改售价、外部下单、押金充值/调整、扣款、释放、Void 和退款必须记录操作人及时间。

## 5. 首版功能模块

### 5.1 登录与客户

- 登录、退出和重置密码。
- 客户账号和用户启停。
- 客户默认 Markup。
- 客户是否允许自行下单。

### 5.2 地址库

- 保存 Shipper 和 Consignee 地址。
- 保存公司名、联系人、电话、邮箱和 Dock Hours。
- 保存常用地址类型及默认 Accessorial。
- 在询价页面快速选择并自动带出资料。

### 5.3 询价

- 起运地、目的地和 Ready Date。
- 多行货物：件数、包装、长宽高、重量、Class、NMFC、Description。
- Residential、Liftgate、Limited Access、Appointment 等服务。
- 同时向已启用的多个渠道请求报价。
- 显示 Carrier、服务、Transit Days、售价和报价有效期。
- 支持按价格和时效排序。

### 5.4 简单定价

首版只做容易理解的加价方式：

- 每个客户一个默认百分比 Markup。
- 可选的每票最低加价金额。
- Admin 可以对单条 Rate 人工修改售价，但必须填写原因。

暂不做 Lane、Carrier、费用项或多层级复杂规则。

### 5.5 下单

- 选择一条有效 Rate。
- 补全联系人、电话、邮箱、营业时间、Reference/PO 和备注。
- 提交前检查价格字段是否改变、Rate 是否过期。
- 提交前检查并原子预占等于该票客户售价的押金；余额不足时不调用外部下单接口。
- 使用幂等控制防止重复点击生成多个外部订单。
- 保存内部订单号、渠道确认号和 PRO（渠道立即返回时）。

### 5.6 BOL

- 优先保存渠道返回的 BOL。
- 渠道不返回统一 BOL 时，可使用平台模板生成。
- 可在订单详情下载和重新打印。
- 文件需要关联订单、类型、生成时间和来源。
- BOL 成功生成后，将该订单的押金预占转为正式扣款。

### 5.7 报价与订单历史

- 报价按 Quote Number、日期和状态查询。
- 订单按 Order Number、Reference/PO、PRO、日期和 Carrier 查询。
- 从历史报价重新询价。
- 从历史订单复制为新的 Quote Draft。
- 一个订单详情页显示地址、货物、价格、确认号、PRO 和 BOL。
- 订单详情显示该票押金的预占、扣款或退款状态。

### 5.8 客户押金

- 每个客户有一个美元押金账户，显示账户余额、预占金额和可用余额。
- `可用余额 = 账户余额 - 预占金额`。
- 首版由 Admin/Operations 线下收款后手工登记充值，不接在线支付。
- 每笔资金变化写入不可删除的押金流水。
- 流水类型至少包括：充值、预占、扣款、释放、Void 退款、人工调整。
- 人工调整必须填写原因；不能直接覆盖余额。
- 客户可以查看本公司的余额和流水，但不能新增充值或修改流水。
- Void 只有在上游渠道确认成功后才退款；退款金额等于该票原始扣款金额。

## 6. 简化页面结构

首版只需要以下页面：

1. 登录。
2. 新建询价。
3. 报价结果/选择 Rate。
4. 补全资料并确认下单。
5. 订单成功页。
6. 报价历史。
7. 订单历史与订单详情。
8. 地址库。
9. 客户管理和简单定价（内部）。
10. 客户押金与流水。
11. 渠道配置（Admin）。

不单独开发 Dashboard；登录后默认进入“新建询价”，同时显示少量最近报价和订单入口。

## 7. 简化状态

### 7.1 Quote

`DRAFT → RATING → QUOTED → RATE_SELECTED → ORDERED`

例外状态：`PARTIAL_RESULTS`、`NO_RATES`、`EXPIRED`、`INVALIDATED`。

### 7.2 Order

`DRAFT → SUBMITTING → BOOKED`

例外状态：`SUBMIT_FAILED`、`CANCELLED`。

首版订单在成功取得渠道确认和单证后即视为流程完成，不继续维护运输生命周期。

### 7.3 Deposit Transaction

正常出单：`RESERVED → CHARGED`

出单失败：`RESERVED → RELEASED`

订单作废：`CHARGED → REFUNDED`

Void 请求与渠道结果必须单独保存；只有渠道确认成功才能进入 `REFUNDED`。

## 8. P0 功能需求

### Epic A：账号和地址

- FR-A01：Admin 创建和停用客户及用户。
- FR-A02：客户数据严格隔离。
- FR-A03：客户和内部用户可以维护地址库。
- FR-A04：从地址库选择地点后自动填充联系人与营业时间。

### Epic B：询价和价格

- FR-B01：创建包含多个货物行和 Accessorial 的 Quote。
- FR-B02：同时请求至少两个报价渠道；测试阶段允许一个真实渠道加一个模拟渠道。
- FR-B03：标准化并展示 Carrier、服务、售价、时效和有效期。
- FR-B04：根据客户默认 Markup 计算售价。
- FR-B05：准确判断价格字段变化并使旧 Rate 失效。
- FR-B06：保存 Quote 和所有返回 Rate。

### Epic C：下单和打印

- FR-C01：选择有效 Rate 并补全非计费资料。
- FR-C02：幂等创建外部 Order/Shipment。
- FR-C03：保存内部订单号、外部确认号和 PRO。
- FR-C04：获取或生成 BOL。
- FR-C05：下单失败时显示可操作的原因并允许安全重试。

### Epic D：历史和复制

- FR-D01：查询报价和订单。
- FR-D02：一个页面展示订单全部资料和文件。
- FR-D03：复制历史订单为新的 Quote Draft。
- FR-D04：复制后必须重新询价，不得沿用旧 Rate。

### Epic E：客户押金与 Void

- FR-E01：Admin/Operations 可以为客户登记充值和人工调整，每次操作必须填写外部收款参考或原因。
- FR-E02：客户和内部人员可以查看余额、预占、可用余额及流水。
- FR-E03：下单前原子检查并预占该票客户售价；可用余额不足时禁止外部下单。
- FR-E04：BOL 成功生成时完成一次且仅一次扣款；下单/BOL 失败时释放预占。
- FR-E05：Void 经上游渠道确认成功后，将原扣款金额一次且仅一次退回押金。
- FR-E06：每笔充值、调整、预占、扣款、释放和退款均关联客户、订单（如适用）、操作人、时间和幂等键。

## 9. 首版验收标准

- 客户 A 无法看到客户 B 的地址、报价、订单和文件。
- 客户页面和接口不包含成本、毛利或渠道凭证。
- 常用地址可以一键带出公司、联系人、电话和营业时间。
- 至少两个渠道可以在同一报价页面返回并比较结果。
- 一个渠道失败时仍能展示另一个渠道的报价。
- 修改联系人不会使 Rate 失效；修改重量或 Accessorial 会使 Rate 失效。
- 过期 Rate 不能下单。
- 押金不足时不能调用外部下单接口或生成 BOL，并明确显示需补充的金额。
- 重复点击提交不会创建多个外部订单。
- BOL 成功生成后只扣除一次该票客户售价，即使页面刷新或接口重试也不会重复扣款。
- 下单或 BOL 失败时，预占押金会释放，不减少账户余额。
- Void 未获渠道确认时不会退款；确认成功后只退回一次原扣款金额。
- 下单成功后可以查看订单号、押金扣款记录并下载 BOL。
- 可以按 Order Number、Reference/PO、PRO、日期和 Carrier 找到订单。
- 复制历史订单后会建立新的 Quote 并重新获取 Rate。

## 10. 推荐开发拆分

| 迭代 | 交付内容 | 演示结果 |
|---|---|---|
| Sprint 0 | 页面线框、字段表、简单数据模型、首个渠道选择 | 产品范围和字段确定 |
| Sprint 1 | 登录、客户、用户、地址库、押金账户与手工充值 | 可以安全登录、复用地址并查看余额 |
| Sprint 2 | 询价表单、货物、Accessorial、校验 | 可以完整填写一票 LTL 询价 |
| Sprint 3 | 渠道适配框架、第一个真实 Rate 接口、Markup | 可以获得并显示真实售价 |
| Sprint 4 | 第二个报价渠道、并行询价、失败隔离 | 可以比较多个渠道 |
| Sprint 5 | 选择 Rate、押金检查/预占、创建订单、失败释放 | 可以使用押金安全完成真实下单 |
| Sprint 6 | BOL、扣款、Void 退款、历史与复制 | 完整询价打单与押金闭环 |
| Sprint 7 | 权限、安全、端到端测试和试点上线 | 首版发布 |

## 11. 最小数据对象

首版仅建立：

- Customer
- User
- Address
- Quote
- QuoteLine
- Rate
- Order/Shipment
- Document
- DepositAccount
- DepositTransaction
- CarrierConnection
- AuditLog

不建立 Pickup、TrackingEvent、POD、Invoice、Payment、Credit、Adjustment 等业务对象。DepositAccount 和 DepositTransaction 只负责预付押金与订单扣退，不扩展为完整会计系统。

## 12. 开发前只需确认的事项

1. 首版是否同时开放客户自行下单，还是先只供 Justnano 内部使用？
2. 第一个和第二个报价渠道选择哪两个？
3. 这两个渠道是否都支持 API 下单和获取 BOL？
4. 默认 Markup 是百分比多少，是否需要每票最低加价？
5. 客户是否看到真实 Carrier 名称？
6. BOL 优先使用渠道版本，还是统一使用 Justnano 模板？
7. 首版是否需要“取消刚创建的订单”；如果需要，必须先核对各渠道取消能力和费用规则。
8. 押金币种是否固定为 USD？
9. Admin 手工充值需要记录哪一种外部收款参考（银行流水号、Zelle、支票号等）？
10. Void 是否始终全额退回原扣款，还是某些渠道 Void Fee 需要从退款中扣除？首版默认全额退款，除非业务规则另行确认。

## 13. 后续功能加入原则

只有当首版稳定使用且实际业务证明有必要时，才新增 Pickup、Tracking、POD、Invoice 或 Rebill。每次只增加一个闭环，不一次扩展成完整 TMS。

建议顺序仅供以后参考：

1. Tracking。
2. POD。
3. Pickup。
4. Invoice/Rebill。

该顺序不属于当前开发范围。
